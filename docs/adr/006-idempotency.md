# 006. Idempotency: stored responses under a tenant-scoped key

- Status: accepted
- Date: 2026-10-28

## Context

A platform retry must have exactly one effect, even while the first request runs (AC-02).

## Decision

`Idempotency-Key` is optional on every POST. The row is `(tenant_id, key, fingerprint,
status_code, response_body)`; the fingerprint is the sha256 of the canonical JSON of method,
route template, path ids and the normalised body. The claim is `INSERT … ON CONFLICT DO NOTHING
RETURNING` inside the business transaction; the response is written in the same transaction.
Same fingerprint: replay the stored response. Different: 422 `idempotency-key-mismatch`, nothing
stored. Business rejections (422, 409, and 404 for an unknown program or reservation) are stored
and replayed, so a new attempt needs a new key (AC-17). Validation and auth errors return before
the key is taken. Infrastructure errors roll everything back, including the key. Without a key,
natural keys deduplicate: one reservation per invoice, one release per `release_ref`. Keys are
kept 24 h or more (NFR-11).

### What takes the key and what does not

The rule (PRD §8 step 1, A13): an answer that **fixing the request** would change must not be
stored. Otherwise the client fixes the request, retries with the same key, and gets 422
`idempotency-key-mismatch` instead of an answer.

| Outcome | Key taken? | Why |
| --- | --- | --- |
| 401, 403 | No | Rejected before the use case runs. |
| 400 `validation-error` (body, scale, size, release currency) | No | The client fixes the request and reuses the key. |
| 201 / 200 | Yes | The effect happened; a retry must see it. |
| 409, 422 business rejections | Yes | The same request gets the same answer (AC-17). |
| 404 `not-found` | Yes | See below. |
| 5xx, timeout, crash | No | Rolled back with the transaction; a retry runs again. |

A release in the wrong currency is a validation error, but only the stored reservation knows
the invoice currency. The use case therefore reads it with a plain `SELECT` before it claims
the key. That is safe outside any lock, because a reservation's currency never changes.

**404 under a key is stored.** In PRD §8 the key is taken before the program is looked up, so
404 is a business outcome like 409. Reservation ids are generated by the server, so a 404 for
a reservation never turns into a hit later. A 404 for a program can (treasury may create the
program afterwards). That retry then replays 404 until the key expires, and a new attempt
needs a new key, the same as AC-17. The rule is documented on the `Idempotency-Key` header.
Rejected: not storing 404s. It adds a special case and makes the same key answer 404 first
and 201 later.

### The `release_ref` row: claimed, then filled or deleted

The release's dedup row is claimed with its result columns (`invoice_amount_minor`,
`amount_minor`, `result`) still `NULL`. In the same transaction it is either **filled**
(success) or **deleted** (a refused release, such as one above the remainder). A `CHECK` ties
the three columns together.

No other transaction ever sees a half-filled row. Under READ COMMITTED an uncommitted row is
invisible, and a concurrent duplicate does not read it: it waits at the unique index for the
winner to end.

- Winner committed a result: the duplicate's insert does nothing, a new statement reads the
  committed result, and it is replayed (or 422 `release-ref-mismatch` if the body differs).
- Winner was refused and deleted its row: the duplicate's insert succeeds, and its release is
  evaluated against the current state.

A refused release leaves no trace, so the same `release_ref` can be retried after a fix (AC-06).
Under an `Idempotency-Key` the refusal is still stored for that key, as in the table above.

The `release_ref` fingerprint covers only `{reason, amount}`: the reservation already scopes
the reference. A final release sent without `amount` and one sent with the exact remainder
are different requests by fingerprint. Clients reuse the same body for a retry.

## Consequences

- No lease or in-progress state: no external call; a crashed claim vanishes with its transaction.

## Alternatives rejected

Redis (PRD §7), a separate transaction for the key (crash window), storing only successes
(a retry could flip a 422 into a 201).
